# Database Migrations Guide (Alembic)

This template uses [Alembic](https://alembic.sqlalchemy.org/) for tracking database schema changes and applying migrations. Alembic is configured to scan all models inheriting from `SQLModel` inside `src/models/` and compare them with the active database schema.

---

## How Migrations Work in this Template

1.  **Metadata Binding:** In `alembic/env.py`, the target metadata is bound to `SQLModel.metadata`.
2.  **Autodetection:** Any SQLModel tables declared (e.g., in `src/models/user.py` or `src/models/api_key.py`) and imported in `alembic/env.py` are automatically tracked.
3.  **Docker Orchestration:** When spinning up Docker Compose, the `migrator` service automatically executes `alembic upgrade head` before the `api` and `worker` services launch, ensuring the schema is always up-to-date.

---

## Running Migrations Inside Docker

When developing using Docker Compose, the codebase is mounted as a volume. Any migration files generated inside the container will be written back to your host machine's directory, and hot-reloads will apply instantly.

### 1. Generate an Autogenerated Migration in Docker
If you modify your models in `src/models/` and want to autogenerate a migration using the database running inside Docker Compose:
```bash
docker compose run --rm api alembic revision --autogenerate -m "Add description to user"
```
The migration file is created inside the container and immediately synced back to your host machine's `alembic/versions/` directory.

### 2. Generate a Blank Migration in Docker
To create a blank script inside the docker containers:
```bash
docker compose run --rm api alembic revision -m "Custom data migration"
```

### 3. Applying Migrations in Docker
Migrations run automatically on `docker compose up`. If you write a new migration file and want to apply it immediately to the running database container without restarting the entire stack, run:
```bash
docker compose run --rm migrator alembic upgrade head
```

To upgrade to a specific revision:
```bash
docker compose run --rm migrator alembic upgrade <revision_id>
```

### 4. Checking Migration Status in Docker
To check the current database schema revision and history inside Docker:
```bash
# Check current version
docker compose run --rm migrator alembic current

# Check migration history
docker compose run --rm migrator alembic history --verbose
```

### 5. Reverting / Rolling Back Migrations in Docker
To revert the last applied migration:
```bash
docker compose run --rm migrator alembic downgrade -1
```

To roll back all migrations to base:
```bash
docker compose run --rm migrator alembic downgrade base
```

## Creating and Running Migrations Locally (Development)

To perform migration operations locally outside of Docker, make sure you have the virtual environment activated, your local database service running, and `.env` configured with `DATABASE_URL` pointing to `localhost` (e.g., `postgresql+asyncpg://postgres:postgrespassword@localhost:5432/app`).

### 1. Generate an Autogenerated Migration
If you add or modify a column on a model (for example, adding a description field to `User`), Alembic can compare the models against the local DB schema and automatically generate the migration scripts.

Run:
```bash
uv run alembic revision --autogenerate -m "Add description to user"
```
This generates a new migration file in `alembic/versions/`.

> [!WARNING]
> **Always review autogenerated files!**
> Alembic's autodetection is powerful but has limitations (e.g. it might not detect table name changes or check constraints). Open the generated script in `alembic/versions/` and verify that the `upgrade()` and `downgrade()` methods are correct.

### 2. Generate a Blank Migration (For Custom/Data Migrations)
If you need to execute raw SQL scripts or perform data migrations (e.g. populating default values or moving data between tables) that cannot be autodetected:

Run:
```bash
uv run alembic revision -m "Custom data migration"
```
This creates a blank script. You can then use `op.execute("UPDATE ...")` or SQLAlchemy constructs inside `upgrade()` and `downgrade()`.

### 3. Apply Local Migrations
To update your local Postgres database to the latest schema version:
```bash
uv run alembic upgrade head
```

To update to a specific version (replace `revision_id` with the actual hash, e.g. `561152849b59`):
```bash
uv run alembic upgrade <revision_id>
```

### 4. Revert / Roll Back Migrations
To undo the last applied migration:
```bash
uv run alembic downgrade -1
```

To roll back all migrations (revert to clean state):
```bash
uv run alembic downgrade base
```

## Migration Troubleshooting & Best Practices

### 1. Adding New Models
If you create a new model file (e.g., `src/models/org.py`):
1.  Ensure it inherits from `SQLModel` (or `TimestampModel`) and has `table=True`.
2.  **Crucial:** Import the model in `alembic/env.py` so Alembic includes it in the metadata scanner:
    ```python
    # alembic/env.py
    from src.models.org import Org
    ```

### 2. Resolving out-of-sync / lock states
If you modify local files but forgot to run migrations, or if two developers create migrations in parallel, you might hit a split-history merge conflict.
To resolve split history, create a merge revision:
```bash
uv run alembic merge heads -m "Merge parallel migration branches"
```

### 3. Alembic History
To view the complete chronological chain of database migrations:
```bash
uv run alembic history --verbose
```
